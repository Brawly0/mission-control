# Mission Control UI audit and improvement plan

Date: 2026-10-29. Recommendations only; no application changes made for this audit.

## Evidence and limits

Visually inspected the installed app at 1920 × 1032: the global shell, Home, Projects, project Chats and transcript recap, Agents grid, Tasks board, task-agent workspace, Changes, Docs vault, Inbox, chat search, Usage, Settings General, Knowledge, Skills, Notebook and Templates. Read corresponding renderer components, design tokens, architecture and recent UI decisions. The development window did not expose an accessibility tree and its capture was clipped, so the installed window supplied the visual baseline.

The source contains newer work than the installed UI, including grouped Settings, search suggestions, responsive task controls, improved project cards and shared connection diagnostics. Preserve and verify these changes before creating overlapping work. See decisions 0032 and 0033. Other agents were actively changing this repository during the audit.

This is a desktop heuristic review, not a user study or a full accessibility certification. Narrow layouts, light mode, setup failures, running-task interactions and keyboard-only flows need a separate validation pass; their behavior was not independently verified here. Loading placeholders observed on Home do not establish a performance defect.

## Direction

Make the daily workflow obvious: resume work, handle an interruption, inspect a result, review changes, continue. Keep the project identity, provider distinction, embedded terminals, split panes and task ownership. Reduce the visual weight of navigation and secondary telemetry. Show detailed controls when their context calls for them.

## External references

- [Linear's 2026 interface refresh](https://linear.app/now/behind-the-latest-design-refresh): quieter navigation, clearer header hierarchy and fewer competing borders. Apply the hierarchy principles while retaining readable text sizes.
- [VS Code custom layout](https://code.visualstudio.com/docs/configure/custom-layout): distinct workspace areas, movable/collapsible panels and density controls. Apply to Agents and project tools.
- [Raycast Action Panel](https://manual.raycast.com/action-panel): one obvious primary action and discoverable contextual secondary actions. Apply to project, chat, task and agent menus.
- [Linear Inbox](https://linear.app/docs/inbox): separate items needing attention from other updates. Apply to approvals, failed runs and completed work waiting for review.
- [GitHub Desktop review](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop?platform=windows): file-list/diff focus and adjustable diff presentation. Apply to Changes; preserve existing review evidence rules.

These products supply patterns. The recommendations below are judgments about Mission Control, not claims that those products implement the proposed behavior.

## Section-by-section recommendations

### 1. Readability and visual system — P0

Home uses many 7–11px labels in `home.css`, even while substantial space remains available. Borders, tinted cards, icon backgrounds and several accent colors make small details compete with primary information.

Use a shared type scale: approximately 13–14px for normal UI content, 12px for secondary labels, 18–24px for page headings. Reserve smaller text for genuinely incidental chart annotations. Standardize spacing and control heights through existing tokens and shared controls. Use cyan for primary actions and selection; reserve status colors for meaning. Keep project colors as identification accents. Offer comfortable and compact density only after the default works well.

Acceptance: all essential labels are readable at 100% zoom; selection, focus and status remain distinguishable without color alone. Check contrast in both themes.

### 2. Sidebar and global header — P0

The expanded secondary navigation pushes projects far down the sidebar. Two detailed provider meters occupy most of the global header, while healthy connection status is repeated in a large sidebar block.

Keep the main destinations visible, make secondary tools collapsible, and give pinned/recent projects more room. Preserve a visible Settings entry or clearly labeled menu. Compress healthy provider usage into short summaries with a details popover; expand warnings when action is useful. Keep connection details in the new shared diagnostics surface.

Acceptance: a user can identify the current page, current project and next action at a glance. Essential header controls fit at the existing minimum width.

### 3. Home — P1

Five launch cards, five statistic cards, two activity heatmaps and another Quick Actions panel create several competing entry points. Open agents appear as small links near the bottom.

Put Continue working first: recent chats, open agents and work needing review. Follow with a compact start area. Move detailed activity and all-time statistics into Usage; retain one restrained overview if useful. Make launch destinations explicit, such as “Codex in Mission Control” versus “Quick chat.” Give unavailable data a bounded error/retry state rather than an ambiguous blank chart.

Acceptance: resuming the last chat is available above the fold; the destination of a new chat is clear before launch.

### 4. Agents workspace — P0

The global header, agent tabs, workspace toolbar, pane header and recap strip stack above terminals. Project and provider identity repeat. Three terminal columns produce heavily wrapped output.

Retain one agent switcher and one compact workspace toolbar. Move grid column counts, broadcast and workspace management into a layout/actions menu. Collapse recap detail after it has served its purpose. Make active input ownership unmistakable. Default Auto layout should respect a minimum useful pane width and offer focus-plus-secondary or tabs when the window is too narrow. Keep Close process clearly distinguished from hiding or switching a view.

Acceptance: more vertical room for terminal content; no session is restarted by navigation; users can identify the input target immediately. Validate with one, three and six agents.

### 5. Tasks board — P1

The four-column lifecycle is understandable. In the observed sparse board, three large empty columns contrast with dense completed-team cards. Queue controls and task-agent navigation add toolbar complexity.

Keep Board and Task agents related but clearly separated from queue settings. Give each card a title, project, meaningful state and one primary action. Put technical execution metadata behind details. Offer a compact list for sparse boards while retaining the board option; collapse or limit old Done items. Preserve the new source work for empty columns and filtered-empty states.

Acceptance: every task state exposes a useful next step, and an empty project selection is distinguishable from an empty workspace.

### 6. Task teams and results — P0

The observed completed team opened on the planner's raw JSON/log output. The task drawer already has result and review capabilities; expose those more directly rather than duplicating them.

When a team finishes, offer an Overview with outcome, final answer, changed files and checks. Keep each agent's terminal and logs one click away. Represent dependencies and blocked reasons near the agent list. Use Review result or Review changes as the completion action; reserve Watch agents for active work.

Acceptance: the user can explain what a completed team delivered without reading planner logs. Preserve result-view and Git-snapshot review evidence requirements.

### 7. Project pages and chat history — P1

The chat list plus transcript preview is a strong existing pattern. The expanded recap can occupy much of the transcript area, and technical chips compete with the title.

Keep the split view. Shorten the default recap to a few meaningful lines, with files and commits expandable. Prioritize chat title, latest useful activity and time in the list. Label new-session provider and destination clearly. Place less frequent handoff and worktree choices in the existing action menu. Align the project header with the same title/action convention as other pages.

Acceptance: resume, preview and provider handoff are understandable; long titles and histories do not crowd out the conversation.

### 8. Changes and review — P0

The observed Changes page has a heading, three review cards, buttons, acknowledgement and command setup above the diff. The review mechanism is valuable but consumes a large part of the work area.

Make file list and diff the primary surface. Replace the review cards with a compact status strip that expands for details or failures. Put command configuration behind Set up checks. Keep commit/review actions anchored and retain acknowledgements and stale-evidence invalidation. Evaluate split/unified and whitespace controls after the basic layout is clear.

Acceptance: a user reaches useful diff content immediately and can still see whether checks/review are current. Never make unreviewed work appear approved through a cosmetic change.

### 9. Inbox — P1

The observed Inbox had one usage warning and a large daily digest. It should emphasize decisions requiring the user's attention.

Group approvals, failed work and results awaiting review above informational alerts. Move the digest below these items or make it collapsible. Show project, reason and a direct action on every item. Make dismissing a notification distinct from resolving the underlying problem.

Acceptance: users can identify the highest-priority interruption without scanning metrics.

### 10. Chats and command palette — P1

The Chats destination currently opens full-text search, while the label suggests a browsable chat library. Global search opens a command palette with actions as well as objects.

Either rename Chats to Search chats, or provide a recent-chat list before a query. Keep project/role filters visible and make result previews easy to scan. Preserve source search suggestions. Extend the existing command palette with clearer object categories and consistent contextual actions before considering a replacement search system.

Acceptance: users know whether they are browsing chats, searching message content or running a command; keyboard behavior remains terminal-safe.

### 11. Docs, Knowledge, Notebook and Briefings — P2

These surfaces have different storage and scope, but their names and entry points make those differences hard to predict. Docs opened on a vault-generation promotion even though many readable files existed. Knowledge showed raw Markdown syntax in the observed document view.

Retain storage behavior while clarifying labels: Project docs, All project docs, Personal/project notes and Session briefings. Default Docs to a useful existing document or a short index; make vault generation a secondary action. Share a consistent reader with rendered/read and edit modes, readable line length, search and optional outline. Put latest-briefing continuation close to the project workflow.

Acceptance: users can predict where a note is saved and which projects a search covers, and can read existing docs without initiating an agent.

### 12. Skills and templates — P2

A large Eco promotion dominates the observed Skills page. Skill names are technical, and template discovery ends in an empty modal.

Make the skill library the main content; reduce Eco to a contextual banner or Spending link. Show plain-language purpose, provider compatibility, source and launch destination. For templates, explain required inputs and offer a few optional, clearly labeled examples without silently creating tasks or schedules.

Acceptance: a user can choose a skill or template by expected outcome and knows where it will run.

### 13. Usage and Settings — P1/P2

Usage mixes provider limits, tokens, inferred plan shares and API-price estimates. A large dollar total can be mistaken for a bill despite explanatory copy. Settings has useful categories; newer General grouping already addresses part of the observed clutter.

Lead Usage with remaining capacity and reset times. Separate Usage limits, Activity and Estimated API value. Put qualifications beside the relevant number and avoid implying comparable units across providers. For Settings, preserve the new grouping; add search and clearer global/project/task scope labels if the number of settings warrants it. Make provider-specific Eco effects explicit.

Acceptance: users can distinguish actual plan capacity from an estimated API equivalent and know which future launches a setting affects.

## Delivery order

1. **Foundation and shell:** typography, spacing, page headers, compact global status and sidebar hierarchy. Produce before/after mockups for Home, Agents and Changes before editing broadly.
2. **Daily work:** Agents layout, completed-team overview, compact review status and Home continuation. Reuse existing data and actions.
3. **Discovery:** chat browsing/search distinction, contextual menus, project/chat polish and Inbox priorities.
4. **Supporting tools:** document reader consistency, Skills/Templates, Usage language and Settings discovery.

Avoid a simultaneous application-wide rewrite. Complete and validate one representative screen before applying its pattern to others. Existing React/CSS tokens and UI primitives are sufficient for the first passes.

## Validation before each pass ships

Compare screenshots at 960×600, 1440×900 and 1920×1080; check dark/light and 100%/125% zoom. Exercise keyboard focus, long project/chat names, empty/loading/error states, missing/stale connection data and multiple agents. Preserve task ownership, PTY continuity, provider routing and review evidence. Use existing isolated smoke fixtures for behavioral checks rather than spending model calls on layout proof.

Suggested usability targets: resume the latest chat in at most two deliberate actions; show the completed task result in one action from its card; make attention items identifiable without scrolling a terminal; keep every essential control available at minimum width. These are proposed targets, not measured results.
